# 02. Конвенции кода

Правила проверяются автоматически (Biome + ESLint, хуки). Текст ниже описывает намерение, а конфигурация собирается из него (`packages/tooling/lint`).

## 1. Общий стиль

- Отступ: 4 пробела. Конец строки LF. Кодировка UTF-8.
- Максимально ООП: классы, наследование базовых классов, внедрение зависимостей. В Angular допускается идиоматичный стиль фреймворка (signals, standalone), но логика живёт в сервисах-классах.
- `type`, а не `interface` (правило `consistent-type-definitions: type`). Исключение возможно только по ADR.
- `any` запрещён. Порядок: generics, затем `unknown`, затем алиас `Any` из `core/ts-utils`. Алиас `Any` определён в единственном месте с пояснением.
- В классах обязательны явные типы у полей, свойств и методов (параметры и возвращаемые значения), включая `public`. Исключение: конструктор.
- Функция или тип, используемые больше одного раза, выносятся в `core/js-utils` или `core/ts-utils` (или в доменный utility-пакет) и используются оттуда.
- Импорт и экспорт типов только в явной форме: `import type { X }`, `export type { X }`.
- Экспортируется только через `src/index.ts`, строго именованные экспорты (`export { A }`, без `export *` и без `default`).
- Все типы модуля (внутренние и публичные) лежат в `src/@types/index.ts`.
- Тесты лежат в `<module>/test/`, зеркалят структуру `src/lib`, имя `*.spec.ts`.

## 2. Именование

| Что | Формат | Пример |
|---|---|---|
| `export const`, `public static readonly` | `UPPER_SNAKE` | `MAX_RETRY_COUNT` |
| Публичные поля, методы, геттеры, сеттеры | `camelCase` | `getOrder` |
| Protected поля, методы, геттеры, сеттеры, опции | `_camelCase` | `_buildQuery` |
| Private поля, методы, геттеры, сеттеры, опции | `__camelCase` | `__cache` |
| Типы и классы | `PascalCase` | `OrderDto` |
| Файлы | `kebab-case.ts` | `order-status.ts` |

## 3. Порядок членов класса

1. Статические поля: public, protected, private.
2. Поля экземпляра: public, protected, private.
3. Статические методы: public, protected, private.
4. Конструктор.
5. Методы экземпляра: public, protected, private.

Реализуется через `@typescript-eslint/member-ordering`.

## 4. Сортировка

- Импорты и экспорты сортируются в файле (группы: внешние пакеты, `@scope`, относительные).
- Внутри конструкции (список импортов в фигурных скобках, ключи union, перечисления) сортировка по алфавиту, где порядок не имеет смысла.

## 5. DTO и контракты

- Источник истины: Zod-схема в пакете `contracts`. Из неё выводятся тип и DTO.
- Один базовый тип сущности. На его основе через `Pick`, `Omit`, `Partial` создаются `CreateDto`, `UpdateDto`, `ResponseDto`.
- Один и тот же контракт используют сервер, веб и мобайл. Декораторы Nest и class-validator остаются только в серверном слое.

## 6. Распределение между Biome и ESLint

| Задача | Инструмент |
|---|---|
| Форматирование (TS, JS, JSON, CSS) | Biome |
| Базовые правила (неиспользуемые переменные, `any`, `import type`, сортировка импортов) | Biome |
| Именование, порядок членов класса, `type` вместо `interface`, явные типы членов класса | ESLint (typescript-eslint) |
| Правила Angular и шаблонов | ESLint (angular-eslint) |
| Границы модулей Nx, запрет импорта Material вне `ui-web` | ESLint (`@nx/eslint-plugin`) |
| i18n: запрет захардкоженных строк в шаблонах | ESLint |

Пересекающиеся правила включены ровно в одном инструменте. Форматирование шаблонов Angular и SCSS проверяется отдельным ADR (поддержка Biome ограничена).

## 7. Генерация конфигов

- Единственный ручной источник: TOML в `packages/tooling/lint`.
- Раннер генерирует `biome.json` и `eslint.config.*` на лету, файлы лежат в `.gitignore`. Пересоздание при `postinstall` и перед каждым запуском, если изменился хеш TOML.
- Раннер умеет: `lint`, `format`, режимы `--staged` и `--affected`, кэш, единый отчёт, код возврата для CI.

## 8. Хуки и CI

| Хук | Что делает |
|---|---|
| pre-commit | Линтинг и форматирование застейдженных файлов через раннер |
| commit-msg | Проверка формата сообщения и того, что файлы принадлежат одному проекту Nx |
| pre-push | Типизация и тесты `affected` |
| CI | Полный линтинг, типизация, тесты, сборка, E2E, проверка i18n-ключей, проверка границ модулей |

Обход хуков (`--no-verify`) запрещён.

## 9. Коммиты

Формат: `<icon> <type>: <rootScope>/<moduleScope>: <message>`

- `rootScope`: `apps`, `packages`, `modules` или `root` (корневые файлы, CI, документация).
- `moduleScope`: путь проекта после корня (может содержать `/`).
- Один коммит затрагивает один проект. Изменения в нескольких проектах делятся на коммиты в порядке зависимостей (сначала типы и контракты, затем потребители).
- Сообщение в повелительном наклонении, до 72 символов.

| Иконка | Тип |
|---|---|
| ✨ | feat |
| 🐛 | fix |
| ♻️ | refactor |
| 🧪 | test |
| 📝 | docs |
| 🔧 | chore |
| ⚡ | perf |
| 🎨 | style |
| 🔒 | security |
| 🏗️ | build |
| 🗃️ | db |

Примеры:
`✨ feat: packages/ui/ui-web: add button component`
`🐛 fix: apps/api: handle expired OTP`
`🔧 chore: root/ci: add affected pipeline`

## 10. Тесты

- Каждое поведение покрыто. Порог не ниже 90% строк и веток для доменных пакетов.
- Интеграционные тесты используют реальные контейнеры БД (Testcontainers), без моков хранилищ.
- E2E на Playwright: регистрация, поиск, проект, заказ у двух вендоров, оплата, доставка, возврат, выплата, чат с инвойсом, жалоба с арбитражем.
- Баг фиксируется сначала падающим тестом.
