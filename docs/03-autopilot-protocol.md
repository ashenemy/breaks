# 03. Протокол автопилота

## 1. Рабочий цикл агента

1. `nx run progress:resume`: восстановить контекст (текущая задача, сделанное, следующее действие).
2. Прочитать файл эпика и релевантные разделы архитектуры.
3. Спланировать подшаги (3–8 штук) и записать их в план задачи через `progress checkpoint`.
4. Для каждого подшага: тест (красный), реализация, тест (зелёный), линтинг, коммит, `progress checkpoint`.
5. Закончить задачу: `progress verify <task-id>`. Только успешная проверка переводит статус в `done`.
6. Взять следующую готовую задачу (все зависимости `done`, статус не `blocked`).

Размер задачи: один проект Nx, до ~400 изменённых строк. Если больше, задача делится в плане (новые подзадачи регистрируются командой `progress split`).

## 2. Definition of Done (для любой задачи)

- Все критерии приёмки из эпика выполнены и автоматизированы.
- Тесты написаны и проходят, порог покрытия соблюдён.
- Линтинг, типизация, сборка проходят. Нет `any`, нет TODO без ссылки на задачу в плане.
- Все строки интерфейса через i18n-ключи, переводы hy, ru, en добавлены.
- Состояния интерфейса: загрузка, пусто, ошибка, нет прав.
- Документация модуля (README: назначение, публичный API, примеры) обновлена.
- Миграции и seed обновлены, если менялась схема.
- Нет секретов в коде и логах.

## 3. Допущения и блокеры

- Неясность: выбрать вариант по приоритету документов (см. README), записать в `docs/decisions/assumptions.md`, продолжить.
- Блокер (нужен внешний секрет, аккаунт, платное действие): статус `blocked`, причина и что требуется записываются в план, переход к следующей независимой задаче.
- Противоречие между документами: решить по приоритету, зафиксировать в ADR.

## 4. Инструмент прогресса (`packages/tooling/progress`)

Цель: показывать общий и текущий прогресс и позволять продолжить с правильного места после зависания компьютера или потери окружения.

### 4.1 Файлы

| Файл | Роль | В git |
|---|---|---|
| `docs/progress/plan.yaml` | Дерево: этап, эпик, задача. Генерируется командой `progress sync` из блоков `tasks:` в файлах `docs/epics/*.md`, вручную не правится | Да |
| `docs/progress/state.yaml` | Статусы задач, даты, коммиты завершения | Да (коммитится при завершении задачи) |
| `.progress/checkpoint.json` | Текущий контекст: задача, подшаги, следующее действие, HEAD, хеши изменённых файлов, время | Нет (локально) |
| `.progress/journal.ndjson` | Журнал событий (каждый checkpoint, verify, split, block) | Нет |
| `docs/progress/REPORT.md` | Сгенерированный отчёт | Да |

Запись checkpoint атомарная (временный файл, fsync, rename), чтобы сбой питания не повредил файл.

### 4.2 Схема задачи

```yaml
- id: E01.03.02
  title: Реализовать сущность Category с деревом и наборами свойств
  epic: E01
  scope: modules/catalog/api        # проект Nx, в котором работает задача
  weight: 3                         # относительный вес (1,2,3,5,8)
  deps: [E00.07.01]
  acceptance:                       # автоматические проверки
    - cmd: nx test catalog-api --testPathPattern=category
    - cmd: nx run catalog-api:lint
  substeps: []                      # заполняется агентом при планировании
  status: todo                      # todo | in_progress | done | blocked
  type: task                        # task | gate
```

Задача типа `gate` (например утверждение макетов) выполняется человеком: статус `done` ставится только командой `progress approve <id>` с записью имени и даты. Агент не может закрыть gate и переходит к независимым задачам.

### 4.3 Команды

| Команда | Что делает |
|---|---|
| `progress status` | Общий прогресс (взвешенный по `weight`), прогресс по этапам и эпикам, текущая задача и процент подшагов, число `blocked`, ближайшие готовые задачи |
| `progress resume` | Сверка checkpoint с git и состоянием; вывод «что сделано, что дальше» и готового промпта для агента |
| `progress checkpoint --note "..."` | Запись текущего состояния после подшага |
| `progress start <id>` | Перевод задачи в `in_progress` |
| `progress verify <id>` | Запуск `acceptance` и проверка DoD; при успехе `done` и запись в `state.yaml` |
| `progress block <id> --reason "..."` | Пометить блокер |
| `progress split <id>` | Разбить задачу на подзадачи в плане |
| `progress sync` | Пересобрать `plan.yaml` из эпиков, сохранив статусы |
| `progress approve <id>` | Одобрение gate-задачи человеком |
| `progress report` | Обновить `REPORT.md` |

### 4.4 Расчёт прогресса

- Общий: сумма `weight` задач в `done` делить на сумму `weight` всех задач плана.
- Текущая задача: взвешенная доля выполненных подшагов. Это приблизительная оценка, помечается как `~`.
- После `resume` при расхождениях (HEAD изменился, файлы не совпадают с checkpoint) прогресс по текущей задаче показывается с пометкой «требует проверки».

### 4.5 Возобновление после сбоя

`progress resume` делает по порядку:
1. Читает `.progress/checkpoint.json`. Если нет, восстанавливает контекст из `state.yaml` и `git log` (последние коммиты ссылаются на id задач в теле).
2. Сравнивает `HEAD` и список изменённых файлов с записанными. Расхождение сообщает.
3. Запускает быстрые проверки последнего завершённого подшага (тесты затронутого проекта).
4. Определяет первый незавершённый подшаг и печатает: задача, выполненные подшаги, следующее действие, незакоммиченные файлы, готовый промпт для вставки в чат Copilot.
5. Если окружение потеряно (чистый клон), восстанавливает только по `state.yaml` и git: текущая задача считается начатой заново, ранее закоммиченные подшаги учитываются по сообщениям коммитов.

Правила, чтобы возобновление работало:
- Агент вызывает `progress checkpoint` после каждого подшага (не реже, чем раз в 10–15 минут работы).
- Каждый коммит содержит в теле `Task: <id>` и `Substep: <n>`.
- Незавершённая работа держится на ветке `autopilot/<task-id>`, чтобы не терять изменения при потере окружения; в конце ветка вливается.

### 4.6 Отображение

Терминальный вывод с полосами прогресса (общий, по этапам, текущая задача) и сгенерированный `REPORT.md`. Опционально статическая HTML-страница отчёта для просмотра в браузере.

## 5. Фаза дизайна (до любой верстки)

Макет в Figma минимален и должен быть доработан агентом по итоговому ТЗ.

1. Агент составляет перечень экранов и состояний из эпиков (`docs/design/screens.md`): для каждого портала список экранов, компонентов, состояний (загрузка, пусто, ошибка, нет прав), адаптив (mobile, tablet, desktop).
2. Агент использует Figma MCP (удалённый сервер) с записью на холст (`use_figma`) и существующие компоненты, переменные и стили. Нужны полный seat Figma и проверка того, что Copilot входит в список поддерживаемых клиентов записи на холст; иначе запасной вариант: дизайн в коде (Storybook как источник истины) с последующей выгрузкой в Figma.
3. Токены сначала синхронизируются в `packages/design/tokens`, а затем дизайн опирается на них.
4. Человек утверждает макеты порциями (по порталам); без утверждения верстка этого портала не начинается.
5. Верстка идёт по эпикам и Storybook-историям.

## 6. Рекомендации по моделям в Copilot

Основная модель: самая современная Claude. Для архитектурных задач, миграций, денежной логики и безопасности использовать самую сильную модель. Для шаблонного кода (CRUD, формы, переводы) допустима более лёгкая модель. Доступность моделей в Copilot проверяется на старте проекта.
