# ADR-0014. Теги проектов и правила границ

Статус: `accepted` (принято агентом по протоколу в задаче E00.01.02; пересматривается человеком).
Дата: 2026-10-04.

## Контекст

`docs/01-architecture.md` (раздел 4) и эпик E00.01 требуют, чтобы границы между проектами обеспечивались
правилом Nx `@nx/enforce-module-boundaries` по тегам `scope:*`, `type:*`, `platform:*`. Эпик задаёт четыре
правила: `web` и `api` не зависят друг от друга, `native` не зависит от `web`, общее живёт в `core` и
`contracts`, `tooling` не импортируется из приложений. Нужно зафиксировать точную семантику тегов и полную
матрицу разрешённых зависимостей, чтобы генераторы (E00.01.03) расставляли теги автоматически, а линтер
отклонял нарушения.

## Решение

### Теги

Каждый проект несёт ровно три тега.

| Тег | Значения | Смысл |
|---|---|---|
| `scope:` | `shared` или имя домена (`catalog`, `orders`, `vendors`, ...) | Доменная принадлежность. `shared` — код без домена: утилиты, общие контракты, UI-наборы, инфраструктура, сквозные модули, приложения и инструменты |
| `type:` | `app`, `module`, `ui`, `infra`, `contracts`, `core`, `tooling` | Роль проекта в слоистой архитектуре |
| `platform:` | `api`, `web`, `native`, `shared` | Среда выполнения: `api` — Node.js (сервер, воркеры, инструменты), `web` — браузер, `native` — NativeScript, `shared` — не зависит от среды |

Соответствие каталогов и тегов по умолчанию (генераторы E00.01.03 следуют ему):

| Каталог | type | platform | scope |
|---|---|---|---|
| `apps/api`, `apps/worker` | `app` | `api` | `shared` |
| `apps/web-*` | `app` | `web` | `shared` |
| `apps/mobile-*` | `app` | `native` | `shared` |
| `modules/<name>/api`, `/web`, `/native` | `module` | по подкаталогу | `<name>`; сквозные модули — `shared` |
| `packages/core/*` | `core` | `shared` | `shared` |
| `packages/contracts/<name>` | `contracts` | `shared` | `<name>` или `shared` |
| `packages/ui/ui-web`, `ui-native`, `ui-contracts`, `packages/design/tokens` | `ui` | `web`, `native`, `shared`, `shared` | `shared` |
| `packages/infra/*` | `infra` | `api` | `shared` |
| `packages/tooling/*` | `tooling` | `api` | `shared` |

### Матрица разрешённых зависимостей

Импорт разрешён, только если он проходит все три группы ограничений. Проект без подходящего ограничения
(без тегов) не может импортировать проекты, а проект без тегов не может быть зависимостью — это
поведение правила Nx, им пользуемся как защитой от непомеченных проектов.

Платформа (код видит только свою среду и общий код):

| Источник | Разрешённые зависимости |
|---|---|
| `platform:api` | `platform:api`, `platform:shared` |
| `platform:web` | `platform:web`, `platform:shared` |
| `platform:native` | `platform:native`, `platform:shared` |
| `platform:shared` | `platform:shared` |

Роль (слои зависят только вниз):

| Источник | Разрешённые зависимости |
|---|---|
| `type:app` | `module`, `ui`, `infra`, `contracts`, `core` |
| `type:module` | `module`, `ui`, `infra`, `contracts`, `core` |
| `type:ui` | `ui`, `contracts`, `core` |
| `type:infra` | `infra`, `contracts`, `core` |
| `type:contracts` | `contracts`, `core` |
| `type:core` | `core` |
| `type:tooling` | `tooling`, `module`, `ui`, `infra`, `contracts`, `core` |

Домен:

| Источник | Разрешённые зависимости |
|---|---|
| `scope:shared` вместе с `type:core`, `contracts`, `ui`, `infra` или `module` | только `scope:shared` |
| `scope:shared` вместе с `type:app` или `type:tooling` (точки сборки) | любой `scope:*` |
| `scope:<домен>` | любой `scope:*` (точечные запреты между доменами добавляются вместе с модулями) |

Следствия: приложения никем не импортируются (дополнительно запрещено самим правилом Nx), `tooling` не
импортируется ничем, кроме `tooling`, общий код не знает о доменах, общий код (`platform:shared`) не
зависит от платформенного.

### Где это живёт

- Данные ограничений: `tools/boundaries/dep-constraints.mjs` (`DEP_CONSTRAINTS`), подключаются в корневом
  `eslint.config.mjs` в правило `@nx/enforce-module-boundaries`. В E00.02 источником становится раздел
  `[boundaries]` в `packages/tooling/lint/rules.toml`, конфиг ESLint генерируется, этот ADR остаётся описанием.
- Проверка: `pnpm test:boundaries` (`tools/boundaries/boundaries.spec.ts`). Тест создаёт временный воркспейс
  в `tmp/` с проектами-фикстурами всех типов и платформ, строит граф Nx и запускает ESLint с реальным
  конфигом: для каждого запрещённого импорта ожидается конкретное сообщение, для разрешённых — отсутствие
  ошибок. Среди негативных кейсов — сценарий эпика: импорт `apps/api` из `modules/catalog/web`.
- Правило работает по кэшу графа проектов, поэтому вне `nx lint` его нужно прогревать (`nx graph`).

## Альтернативы

- Только четыре правила из эпика как `notDependOnLibsWithTags`: отклонено, списки разрешённого
  (`onlyDependOnLibsWithTags`) закрывают и неперечисленные комбинации, в том числе проекты без тегов.
- Отдельный scope для приложений (`scope:app`): отклонено, достаточно комбинированных ограничений
  `allSourceTags`, а набор значений `scope:` остаётся «домен или shared», как в эпике.
- Запрет зависимостей между доменами с первого дня: отклонено, доменные модули заведомо зависят друг
  от друга (заказы от каталога); запреты вводятся адресно при появлении модулей.

## Последствия

- Генераторы E00.01.03 обязаны ставить все три тега; CI-проверка «проект создан генератором» дополняется
  проверкой наличия тегов.
- Новый тип или платформа добавляются в `dep-constraints.mjs`, в этот ADR и в тест одновременно.
- `tools/boundaries` — корневой скрипт воркспейса, а не проект Nx (допущение A-010).
