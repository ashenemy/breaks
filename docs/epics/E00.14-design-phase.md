# E00.14. Фаза дизайна: доработка макетов в Figma

Этап: M0.5. Зависимости: E00.06 (токены), E00.11.01 (Storybook), эпики M1–M7 (для составления перечня экранов).
Верстка любого портала начинается только после утверждения его макетов человеком.

## Цель
Дополнить минимальный макет в Figma до полного набора экранов и состояний по ТЗ, опираясь на токены и компоненты проекта.

## Требования
1. Перечень экранов `docs/design/screens.md` генерируется из эпиков: для каждого портала (admin, vendor, buyer-web, buyer-mobile) список экранов, компонентов и состояний (загрузка, пусто, ошибка, нет прав, офлайн для мобайла), адаптивных вариантов (mobile, tablet, desktop), локализационных вариантов (hy и ru с длинными строками), тёмной темы.
2. Работа с Figma через удалённый MCP-сервер Figma с записью на холст (инструмент `use_figma`) и существующие компоненты, переменные, стили. Нужны полный seat и поддержка записи выбранным клиентом (ADR-0010).
3. Запасной путь, если запись из Copilot недоступна: дизайн в коде (Storybook как источник истины, экраны как истории) и выгрузка в Figma по возможности; макеты утверждаются по Storybook.
4. Перед работой токены Figma синхронизируются с `design/tokens` (E00.06.06). Агент не создаёт новые цвета и размеры в обход токенов.
5. Порядок: общие паттерны (шапка, навигация, формы, таблицы, пустые состояния) затем порталы партиями. После каждой партии человеку отправляется список экранов со ссылками на фреймы и чек-лист проверки.
6. Для каждого экрана фиксируются: сценарий, данные, права, состояния, ключи i18n (имена ключей совпадают с будущими ключами в коде).
7. Утверждение фиксируется в `docs/design/approvals.md` (портал, дата, версия файла Figma, замечания).

## Критерии приёмки
- Для каждого экрана есть фреймы всех состояний и адаптивных вариантов, они используют только компоненты и переменные проекта.
- Утверждение каждого портала записано человеком; без записи задачи верстки этого портала остаются заблокированными.
