# E03.03. Корзина, оформление, заказы из нескольких вендоров

Этап: M3. Зависимости: E01.03, E03.02, E00.05.05.

## 1. Цель
Корзина, пошаговое оформление, разбиение заказа на подзаказы по вендорам, графики доставки, жизненный цикл заказа и интерфейс покупателя.

## 2. Сущности и статусы
- **Cart**: гость или пользователь, позиции (вариант, количество в базовой единице, отображение в упаковках), метки изменений цены и остатка.
- **Order** (оформление покупателя): `number`, `buyerId`, `contact`, `address`, `currency` расчёта, `totals`, `snapshotRates`, `status`.
- **SubOrder** (на вендора): позиции со снимками (название, цена, свойства, налоги, комиссия), `deliveryPreference`, итоги, статус.
- **Shipment**: рейс доставки подзаказа, состав позиций, окно, статус (ведётся в E06.02).
- **DeliveryPreference**: `ready_each` (отправлять по мере готовности), `all_ready` (одной отправкой, когда всё готово), `scheduled` (на выбранную дату и окно).

Статусы подзаказа: `pending_payment` → `awaiting_vendor` → `accepted` → `preparing` → `ready` (или `partially_ready`) → `in_delivery` → `delivered` → `confirmed` → `completed`. Ветки: `cancelled_by_buyer` (до принятия вендором, позже по правилам), `cancelled_by_vendor`, `return_requested` → `returned`, `dispute` (открыта жалоба, E04.03). Подтверждение (`confirmed`): покупатель подтверждает получение или система подтверждает автоматически через N дней после `delivered` (настройка). Статус заказа выводится из подзаказов: `pending_payment`, `paid`, `in_progress`, `completed`, `cancelled`, `partially_cancelled`. Таблица допустимых переходов, ролей и побочных эффектов хранится как данные и покрыта тестами.

## 3. Требования
- **Корзина**: гость (по идентификатору в cookie, TTL по настройке) и пользователь; изменение количества с учётом единиц, упаковок, шага, минимальной партии, ценовых ступеней; пересчёт цен; обнаружение изменений цены и остатка до оформления с понятным сообщением; группировка по вендорам; сохранение между устройствами для вошедших; слияние при входе.
- **Оформление** (шаги: контакты и адрес, доставка по каждому вендору, оплата, подтверждение): резервирование остатков с TTL; расчёт итогов по подзаказам; выбор способа доставки для каждого подзаказа (`ready_each`, `all_ready`, `scheduled` с датой и окном из доступных); стоимость доставки по порту `DeliveryQuotePort` (реализуется в E03.07); скидка лояльности по порту `LoyaltyPort` (E03.08); инициирование платежа по порту `PaymentPort` (E03.04); идемпотентность по ключу оформления; создание заказа и подзаказов одной транзакцией со снимками и курсом; номер заказа читаемого формата.
- **Жизненный цикл**: принятие вендором в срок (иначе автоотмена с возвратом по настройке), автоподтверждение получения, отмена покупателем (правила по статусам: полная до принятия, позиционная и частичная по согласию вендора после), отмена вендором с причиной и последствиями, частичная доступность (позиция отсутствует: предложить замену или отменить позицию с перерасчётом), события в леджер и уведомления.
- **График готовности и отправки**: вендор указывает дату готовности позиций; для `ready_each` формируются отправки по партиям готовности, для `all_ready` одна отправка после готовности всех позиций, для `scheduled` окно доставки проверяется на допустимость.
- **API чтения** для покупателя, вендора и админа с фильтрами, пагинацией и правами.
- **Интерфейс покупателя** (web): страница корзины, шаги оформления, страница подтверждения, история заказов, детали заказа с таймлайном по подзаказам и отправкам, подтверждение получения, повторный заказ.

## 5. Права, аудит, события
Права по областям (покупатель видит свои заказы; вендор свои подзаказы; админ все). События `order.created`, `suborder.status_changed`, `order.cancelled`. Аудит ручных действий админа.

## 6. Уведомления
Заказ создан, оплачен, принят вендором, готов, отправлен, доставлен, требуется подтверждение, отменён, изменён состав.

## 7. Ключи i18n
`buyer.cart.*`, `buyer.checkout.*`, `buyer.orders.*`, `order.status.*`.

## 8. Угрозы и меры
Манипуляция ценами и количествами (сервер берёт данные из снимков и резерва), двойное оформление (идемпотентность), перерасход остатков (атомарный резерв), IDOR по номерам заказов (проверка владельца, непредсказуемые идентификаторы), злоупотребление отменами (лимиты и аудит).

## 9. Критерии приёмки
- Заказ из товаров двух вендоров создаёт один заказ и два подзаказа со своими статусами, снимками и графиками доставки.
- Параллельные оформления последнего остатка не дают перепродажи.
- Повтор запроса оформления с тем же ключом не создаёт второй заказ.
- Невалидные переходы статусов отклоняются, таблица переходов покрыта тестами.
- Автоподтверждение и автоотмена срабатывают по расписанию настроек.

## 10. Вне объёма
